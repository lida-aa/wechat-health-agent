# 项目知识文档

## 项目一句话定位

这是一个接入微信渠道的健康管理 Agent Demo，重点展示大模型如何在可信身份、工具权限、人工确认、持久化、失败恢复和隐私约束下进入真实业务流程。

它不是“万能聊天机器人”，也不是医疗诊断产品。

## 为什么做这个项目

普通聊天 Demo 往往只证明“能调用模型”。本项目选择健康管理，是为了展示更完整的后端与 Agent 工程问题：

- 模型不能决定用户身份和权限。
- 查询与写入需要不同的风险等级。
- 敏感写操作必须由用户确认。
- 重复确认、服务重启和发送失败不能造成重复数据。
- 健康信息需要最小化日志、用户隔离和明确免责声明。
- Agent 行为需要可重复评测，而不只靠人工聊天体验。

## 业务范围

当前围绕个人健康管理提供：健康档案、用药计划、生命体征、体检报告、饮食记录、健康计划、健康提醒、症状初筛、附近药店和健康知识库。

症状与报告能力只提供风险提示、复核建议和就医分流，不确诊、不替代医生或药师。紧急风险应引导用户及时联系急救或线下医疗机构。

## 核心工程决策

### 1. 单 Agent、受限工具

当前不拆多 Agent。旅游、娱乐、订单等方向已经删除，保留一个健康 Agent 和一组明确白名单工具。这样能先把权限、状态和数据链路做可靠，避免多个 Agent 放大错误和调试成本。

### 2. 模型是规划者，不是授权者

模型负责理解语言并提出工具调用。后端负责校验工具是否允许、注入真实微信用户身份、判断风险等级并执行状态迁移。即使模型生成恶意或错误参数，也不能跨越这些边界。

### 3. 写操作使用 HITL

记录血压、添加药物、保存报告、创建提醒等操作先生成草稿。用户可以确认、修改或取消；确认时通过原子状态迁移保证只执行一次。

### 4. MySQL 是健康数据事实源

健康档案统一保存为 `health_record` 聚合文档。旧 JSON 只支持一次性导入，避免多份数据同时写入导致不一致。提醒单独持久化，以支持调度、重试和状态查询。

### 5. 隐私优先的可观测性

日志、Trace 和审计保留排错所需的动作、状态、耗时和异常类型，不保存完整健康正文、图片或敏感工具参数。

## 面试时怎么介绍

建议先说业务问题，再说技术：

> 我做的不是一个单纯调用大模型 API 的聊天机器人，而是一个面向微信渠道的健康管理 Agent。我重点解决了模型进入业务后的工程问题：微信会话提供可信用户身份，工具使用白名单和风险分级，健康写操作先生成草稿并要求用户确认，MySQL 和 Redis 保证状态可恢复，提醒任务支持去重和重试，同时用 Agent Eval 验证安全拒绝和工具选择。

如果被问“为什么是微信”，可以回答：微信只是用户触达渠道，项目并非腾讯内部产品；选择它是因为小公司已有微信生态入口，能够让 Agent 进入真实消息、真实身份和长期陪伴场景，而不是停留在网页聊天框。
